# خواندن لاگ‌ها

با `LOG_LEVEL=INFO` رویدادهای اصلی و هر ۶۰ ثانیه یک گزارش `Status` ثبت می‌شود.
زمان‌ها UTC هستند. شناسه‌های `job_id`، `source_id`، `destination_id` و `msg_id`
برای دنبال‌کردن یک پیام در لاگ‌های دریافت، گارد و ارسال استفاده می‌شوند.

| عبارت | معنی |
|---|---|
| `Message received` | پیام دریافت شده؛ `waiting` تعداد منتظرهاست |
| `Processing started` | شروع پردازش؛ `queue_wait` مدت انتظار در صف است |
| `Local guard ... next=AI` | اطمینان قواعد محلی کافی نبوده و مدل بررسی می‌کند |
| `AI guard request` | درخواست مدل، طول ورودی، سقف زمان و خروجی |
| `AI guard failure` | نوع خطا، کد HTTP در صورت وجود یا خروجی نامعتبر |
| `circuit=open` | پس از خطاهای متوالی، درخواست‌های AI موقتاً متوقف شده‌اند |
| `retry_in` | زمان باقیمانده تا امکان تلاش بعدی؛ بازفرستادن خودکار پیام قبلی نیست |
| `AI recovered` | درخواست جدید موفق شده و وضعیت خطا پاک شده است |
| `Guard decision` | منبع تصمیم، برچسب، اطمینان، استفاده از کش و مدت پردازش |
| `action=PUBLISH / DROP / REVIEW` | اجازه ارسال / حذف / عدم ارسال و نیاز به بررسی |
| `Transfer progress` | تعداد پردازش‌شده، موفق، ردشده و ناموفق در انتقال دستی |

در `Status` اتصال Telethon، فعال بودن تنظیم انتقال خودکار و شنوندهٔ آن جداگانه
نمایش داده می‌شوند. `processing` مشغول بودن انتقال خودکار، `waiting` طول صف و
`auto` شمارندهٔ نتایج انتقال خودکار را نشان می‌دهد. بخش `guard` آمار همهٔ بررسی‌های
گارد و نسبت درخواست‌های AI به پیام‌ها را دارد. شمارنده‌ها از شروع همین پردازش هستند
و بعد از راه‌اندازی مجدد صفر می‌شوند؛ شمارندهٔ گارد تضمین ارسال موفق به تلگرام نیست.

لاگ‌ها در خروجی برنامه (از جمله لاگ اجرای Railway) قابل مشاهده‌اند.
با `LOG_TO_FILE=true` در `logs/app.log` هم ذخیره می‌شوند؛ `logs/error.log`
هشدارها و خطاها را نگه می‌دارد. هر فایل تا ۱۰ مگابایت و پنج نسخهٔ قبلی نگه داشته
می‌شود. برای جزئیات بیشتر موقتاً `LOG_LEVEL=DEBUG` تنظیم کنید.
رویدادهای وضعیت و گارد متن پیام، پاسخ خام مدل، کلید API یا سشن را ثبت نمی‌کنند.
